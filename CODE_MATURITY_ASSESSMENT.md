## 1. Type safety & runtime validation — **3 / 4**

**Evidence:**
- `tsconfig.base.json` enables `strict: true`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `forceConsistentCasingInFileNames`, `isolatedModules`, `declaration`, `declarationMap`, `sourceMap`. Module mode `NodeNext`, ES2022 target.
- Every package re-extends the base (`tsc -p tsconfig.json` build script in each `package.json`).
- `zod ^3.24.1` is a direct dep of `@private-mpp/per-client` and `@private-mpp/agent`. `tryParseHealth` / `tryParseSplBalance` use `safeParse`; `createPerTools` validates each tool input via Zod schemas before forwarding to PER.
- `PerClientResult` distinguishes raw `data` from optional `parsed` so unknown fields survive untouched (forward-compat).

**Gaps:**
- No project-level `eslint` / `tsc --noEmit` CI gate.
- Some return types are inferred (`PerClientResult<T>`); explicit narrowing is sparse on the boundary surface.

**Recommendation:** add `pnpm typecheck` (`tsc -b --noEmit`) + `eslint --max-warnings=0` to a CI job before bumping this category.

## 2. External/internal review readiness — **2 / 4**

**Evidence:**
- Three SARIF artifacts under `security/reports/` (`results-owasp.sarif`, `results-security-audit.sarif`, `results-trailofbits.sarif`) — Semgrep OSS scans, all currently 0 findings.
- `security/PrivateMPP-threat-model.md` and `security/security_best_practices_report.md`.
- `security/supply-chain-risk-auditor/results.md` evaluates 10 dependencies (no high-risk).
- `docs/architecture-low-level.md` includes an OWASP-LLM checklist mapped to in-repo mitigations.

**Gaps:**
- No CI; the SARIF outputs are local artifacts, not part of an enforced pipeline.
- No SECURITY.md / responsible-disclosure policy.
- No third-party review yet (project is pre-mainnet).

**Recommendation:** wire Semgrep + `trailmark augment` into a GitHub Actions workflow that fails the build on any new finding above `medium`.

## 3. Access control & secret handling — **2 / 4**

**Evidence:**
- `.gitignore` excludes `.env`, `.env.*.local`, `.idea/`, `.vscode/`, `.DS_Store`, build outputs.
- `.env.example` only contains placeholders; comments explicitly say "never commit real values".
- `apps/web/app/api/example-paid/route.ts` returns **HTTP 503** when `MPP_SECRET_KEY`/`MPP_TEMPO_*` are unset — explicit fail-closed design.
- Agent tools are intentionally narrow: `per_health`, `per_balance`, `per_deposit` only; `transfer`/`withdraw` deliberately omitted ("until HITL policy exists" — `architecture-low-level.md`).

**Gaps:**
- `payResource` accepts an arbitrary URL from a tool argument — documented but not yet allowlisted in code.
- `process.env.OPENROUTER_API_KEY` and PER bearer tokens flow through `chatCompletion` / `PerPaymentClient.request` without any logging redaction layer (only "no logging" by convention).
- No `Authorization`-header redaction in `parseJsonSafe` / `enrichParsed`.
- No HITL gate primitive in code yet.

**Recommendation:** add a host-allowlist module consumed by `payResource`; add a `redactSecrets()` step in `PerPaymentClient.request` so any future `console.log` of `data` is safe by default.

## 4. Code complexity & cohesion — **3 / 4**

**Evidence (from trailmark):**
- 41 functions/methods analyzed; **zero** with cyclomatic complexity > 6.
- Top three: `createPerTools` (CC=6), `chatCompletion` (CC=5), `payResource` (CC=5). All others ≤ 4.
- Two classes total (`PrivateMppAgent`, `PerPaymentClient`); single-responsibility per class.
- 1,591 LOC across 17 source files (per `wc -l` on `packages/*/src/**` and `apps/web/app/**`). Tight scope.

**Gaps:**
- `createPerTools` is starting to act as a god-builder; it's the natural place where new tools land and will grow over time.
- `PerPaymentClient` has 13 public methods on one class — they're trivial wrappers, but a future refactor into per-resource modules will help.

**Recommendation:** keep CC≤6 as a soft cap and split `createPerTools` per tool family (read-only vs. money-moving) before adding HITL gates.

## 5. Operational decentralization (TS adaptation) — **2 / 4**

**Evidence:**
- All PER calls are HTTPS-only via `PerPaymentClient`; base URL comes from env, never hard-coded.
- `mppx` credential verification happens at the route handler — no third-party identity service.
- No on-chain admin keys in this repo (PER is REST; Solana program code is explicitly out of scope per PRD).
- Workspace dependencies are pinned via `pnpm-lock.yaml`.

**Gaps:**
- `MPP_TEMPO_RECIPIENT` defaults to a single recipient in `.env.example` — fine for a stub, but a real deployment needs runtime-configurable receivers + a registry.
- No multi-key signing or distributed verification path yet.

**Recommendation:** document the trust model for `MPP_SECRET_KEY` rotation and consider per-tenant keys before mainnet.

## 7. Replay / nonce / 402-credential risks (MEV-equivalent) — **1 / 4**

**Evidence:**
- Repo relies on `mppx`'s credential verification at the `apps/web/app/api/example-paid/route.ts` handler — not a custom implementation.
- `mpp-custom-stub.ts` is a stub (`verifyPerBackedCredentialStub`) for future PER↔MPP bridging; not wired in.

**Gaps:**
- No replay-protection logic owned by this repo (timestamps, nonce store, idempotency keys). The dependency on `mppx` is correct, but there is no in-repo test or assertion that demonstrates a replayed credential is rejected, no rate-limit, and no anti-flood guard.
- No idempotency on `pay_resource` (the agent could re-pay).

**Recommendation:** add explicit replay tests once Vitest is in (see `GENOTOXIC_REPORT.md` → step 2). Add an idempotency-key cache for `payResource` in `packages/agent`.

## 8. Low-level / unsafe code — **2 / 4**

**Evidence:**
- Three direct `fetch()` callers: `chatCompletionFetchFallback`, `payResource`, `PerPaymentClient.request`. Each has its own error path.
- `parseJsonSafe` swallows JSON parse errors and returns the raw text — intentional, but a footgun if a caller treats "parsed === undefined" as "data is plaintext".
- Process env is read in three places (`agent.ts`, `cli.ts`, `openrouter-chat.ts`) — could be centralized via the existing `loadBridgeEnv` pattern.
- `isolatedModules: true` and `forceConsistentCasingInFileNames: true` in tsconfig prevent the worst ESM footguns.

**Gaps:**
- No timeouts on `fetch` calls — a malicious or slow PER backend could hang the agent indefinitely.
- No `AbortController` plumbing.
- No retry/backoff strategy yet (PRD mentions it for P1).

**Recommendation:** centralize `fetch` behind a single `httpClient.ts` with default `AbortController` + timeout + structured logging.

## Cross-cutting observations

- The codebase is **small, well-typed, and documented** — typical "Adequate / Good" P0 scaffold scoring. No "Strong" categories yet.
- The single largest gap is **testing (0/4)**, which compounds: it suppresses score on Categories 7 (replay testing), 8 (untested fetch wrappers), and 4 (no regression cap on complexity).
- The second largest is **operational policy gaps** in Category 3: documented intent (allowlists, HITL) without code-level enforcement.
- Static-analysis posture is currently silent (Semgrep clean) — that is a *baseline*, not evidence of strength; mature posture requires the scans to run on every PR.
